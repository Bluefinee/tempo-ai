# 仕様書と実装の QA 検証

対象ドキュメント: $ARGUMENTS

## 検証プロセス

### Phase 1: ドキュメント分析

1. 指定されたドキュメントを読み込む
2. 以下を抽出・整理:
   - 機能要件（MUST/SHOULD/MAY）
   - API 定義（エンドポイント、リクエスト/レスポンス形式、ステータスコード）
   - データモデル・型定義
   - ビジネスロジック・計算式
   - エラーハンドリング仕様
   - 境界条件・制約
   - 非機能要件（パフォーマンス、セキュリティ等）

### Phase 2: 実装調査

1. 仕様で定義された各項目に対応するコードを特定
2. 使用するコマンド:
   - `Glob` で関連ファイルを検索
   - `Grep` でキーワード・関数名を検索
   - `Read` で実装詳細を確認

### Phase 3: 整合性検証

各仕様項目について以下を確認:

#### 3.1 存在チェック

- [ ] 仕様で定義された機能が実装されているか
- [ ] 実装はあるが仕様に記載がない機能はないか

#### 3.2 型・インターフェース検証

- [ ] API のリクエスト/レスポンス型が仕様と一致するか
- [ ] データモデルのフィールド名・型が一致するか
- [ ] Enum 値・定数が一致するか

#### 3.3 ロジック検証

- [ ] 計算式・アルゴリズムが仕様通りか
- [ ] 条件分岐が仕様を正しく反映しているか
- [ ] エラーハンドリングが仕様通りか

#### 3.4 境界条件

- [ ] 入力値の制約（min/max/length 等）が実装されているか
- [ ] Null/undefined/空文字の扱いが仕様通りか
- [ ] エッジケースの考慮

### Phase 4: 問題分類・報告

発見した問題を以下のカテゴリで分類:

```
🔴 CRITICAL: 仕様と実装が明確に矛盾
🟠 MISSING: 仕様にあるが実装されていない
🟡 UNDOCUMENTED: 実装はあるが仕様に記載なし
🔵 UNCLEAR: 仕様が曖昧で検証不能
⚪ QUESTION: 確認が必要な疑問点
```

## 出力フォーマット

検証結果は以下の形式で報告:

```markdown
# QA 検証レポート

## 検証対象

- ドキュメント: [ファイルパス]
- 実装: [対象ディレクトリ/ファイル]
- 検証日時: [日時]

## サマリー

| カテゴリ        | 件数 |
| --------------- | ---- |
| 🔴 CRITICAL     | X 件 |
| 🟠 MISSING      | X 件 |
| 🟡 UNDOCUMENTED | X 件 |
| 🔵 UNCLEAR      | X 件 |
| ⚪ QUESTION     | X 件 |

## 詳細

### 🔴 CRITICAL: 仕様と実装の矛盾

#### [Issue ID]: [タイトル]

- **仕様**: [ドキュメントの記載内容と場所]
- **実装**: [実際のコードと場所]
- **矛盾内容**: [具体的な差異の説明]
- **推奨対応**: [仕様修正 or 実装修正]

### 🟠 MISSING: 未実装機能

#### [Issue ID]: [タイトル]

- **仕様**: [ドキュメントの記載内容と場所]
- **検索結果**: [関連実装が見つからなかった旨]
- **影響範囲**: [この機能がないことの影響]

### 🟡 UNDOCUMENTED: 仕様にない実装

#### [Issue ID]: [タイトル]

- **実装**: [コードの内容と場所]
- **推奨対応**: [仕様への追記 or 実装削除]

### 🔵 UNCLEAR: 曖昧な仕様

#### [Issue ID]: [タイトル]

- **仕様**: [曖昧な記載内容]
- **曖昧な点**: [何が不明確か]
- **確認事項**: [明確化すべきポイント]

### ⚪ QUESTION: 確認事項

#### [Issue ID]: [質問内容]

- **背景**: [なぜこの質問が生じたか]
- **選択肢**: [考えられる解釈]
```

## 検証の優先順位

1. **最優先**: API 定義、データモデル、認証・認可
2. **高**: ビジネスロジック、エラーハンドリング
3. **中**: バリデーション、境界条件
4. **低**: 非機能要件、コメント・ドキュメント

## 注意事項

- 仕様の「意図」と実装の「動作」の両方を考慮
- 明らかな typo や軽微な表記揺れは無視
- 実装が仕様より優れている場合は仕様更新を推奨
- 判断に迷う場合は ⚪ QUESTION として報告
